# FS-004 — Repo-Spec-Aware Application Repositories

functional_set: FS-004
design_revision: ac7cca859e6027461f9a23694fb7d8cf38ae026a

## Purpose

FS-004 realizes DP-102 for repo-spec-aware `split-git` application repositories.

It extends the accepted FS-001 through FS-003 Git-backed realization so newly generated `split-git` repositories:

- install the repo-spec repository-development lifecycle only into the Ruleset repository;
- keep the Dataset repository outside the repo-spec product-development lifecycle;
- preserve inherited ADR application-instance, Ruleset, Dataset, binding, compatibility, transition, and initialization semantics;
- preserve determinate Ruleset/Dataset binding while the two repositories evolve independently;
- consume one exact accepted repo-spec framework revision as a construction input;
- keep repo-spec framework state distinct from repository-specific Ruleset product state, runtime Ruleset material, Dataset state, construction provenance, and `init-config/`;
- remain independently usable after App Builder construction completes;
- provide mechanically decidable validation of the generated repository pair.

FS-004 does not redefine upstream ADR semantics and does not change the accepted lifecycle behavior of `single-file`, `split-files`, or `single-git`.

## Lifecycle Eligibility

Repo-spec lifecycle management applies only to the Ruleset repository generated by `split-git`.

Under FS-004:

- `single-file` does not receive repo-spec lifecycle material;
- `split-files` does not receive repo-spec lifecycle material;
- `single-git` does not receive repo-spec lifecycle material;
- every `split-git` Ruleset repository receives the repo-spec repository-development lifecycle; and
- the paired `split-git` Dataset repository does not receive repo-spec Design, Planning, Build, Semantic Review, or Acceptance lifecycle material.

There is no independent lifecycle-selection option for `split-git`.

Selecting `split-git` selects the FS-004 lifecycle contract.

Provider profiles shall not enable, disable, reinterpret, or alter this lifecycle eligibility.

## Split-Git Ruleset Repository

The generated Ruleset repository is the repository-development home for the application-rule product.

It shall:

- contain the reusable repo-spec framework required for Design → Planning → Build → Validation → Semantic Review → Acceptance;
- remain structurally ready for repository-specific Ruleset product development;
- preserve accepted runtime Ruleset realization at its runtime location rather than requiring relocation beneath `product/`;
- distinguish repo-spec framework-owned state from repository-specific product-development state and accepted runtime Ruleset material;
- avoid presenting generic App Builder-generated bootstrap scaffolding as accepted future Product Design.

Ruleset product development may later define application-specific Dataset schemas, invariants, validation, compatibility, migration, and other Ruleset-owned semantics through the installed lifecycle.

FS-004 construction shall not invent those application-specific semantics merely to populate repo-spec surfaces.

## Split-Git Dataset Repository

The generated Dataset repository remains independently evolving application-instance persistence.

It shall not become a repo-spec product-development repository.

Ordinary Dataset operation, persistence, and repository history evolution remain application-instance activity rather than Ruleset product development.

Ruleset-owned validation, compatibility, migration, refusal, recovery, or related mechanisms may be installed into or invoked from the Dataset repository when required by the generated realization.

Physical installation or execution in the Dataset repository shall not transfer semantic authority to the Dataset and shall not install repo-spec product-development lifecycle ownership there.

## Ruleset/Dataset Binding

The generated Ruleset and Dataset repositories shall preserve enough identity or traceability to determine the applicable Ruleset authority for Dataset operations whenever that distinction is consequential.

The binding shall remain determinate while the repositories evolve independently.

Binding information shall remain distinct from:

- ADR provenance;
- App Builder construction provenance;
- repo-spec framework source provenance;
- ordinary Git history; and
- Dataset committed-state values.

Binding information is not an independent semantic authority and does not transfer committed-state authority away from the Dataset.

The concrete binding representation is a Planning/Build realization choice. FS-004 does not require one universal version field, Git reference, file format, or lookup protocol.

A consequential change in applicable Ruleset authority shall rely on inherited Ruleset-owned compatibility, migration, acceptance, refusal, recovery, or related semantics rather than silently reinterpreting incompatible committed Dataset state.

## Initialization Determinacy

The generated `split-git` realization shall preserve enough information for a fresh reasoning operation to determine:

- application identity;
- selected application-instance identity;
- applicable Ruleset authority;
- relevant authoritative Dataset state; and
- required Ruleset/Dataset binding information.

Ordinary initialization shall not depend on prior conversational memory, the App Builder checkout, or the supplying repo-spec checkout.

FS-004 does not prescribe one universal representation for that information.

## Repo-Spec Source

Every FS-004 `split-git` build shall consume one exact accepted repo-spec framework revision.

The selected source shall be identified truthfully and exactly enough to determine the framework revision installed into the Ruleset repository.

App Builder shall not silently substitute another repo-spec revision while representing the generated repository as having been constructed from the selected source.

The exact source-selection interface, accepted-state verification mechanism, local/remote/archive transport, and source-resolution procedure are Planning/Build concerns.

## Installed Framework Meaning

The generated Ruleset repository installs reusable repo-spec framework material, not the repo-spec initializer product's own repository-specific product semantics.

Framework-owned state shall remain distinguishable from:

- repository-specific Ruleset product-development state;
- accepted runtime Ruleset material;
- runtime Dataset state;
- App Builder construction provenance; and
- `init-config/` construction inputs.

Generated product-development scaffolding may establish generic repo-spec lifecycle surfaces but shall not invent application-specific normative requirements, schemas, validators, migration semantics, or implementation.

## Post-Construction Independence

After successful construction:

- the Ruleset repository shall support its installed repo-spec lifecycle without requiring the App Builder checkout or supplying repo-spec working tree;
- the Dataset repository shall remain usable as application-instance persistence according to the generated realization and applicable Ruleset binding; and
- App Builder shall not become the runtime, save, commit, Planning, Validation, migration, or upgrade service.

A later App Builder invocation is a separate realization operation.

A later repo-spec framework upgrade is a Ruleset-repository development operation governed by the installed lifecycle and applicable repo-spec upgrade semantics.

## Provenance and Determinism

The generated Ruleset repository shall preserve sufficient exact source information to identify the repo-spec framework revision installed during construction.

Repo-spec source lineage shall remain distinguishable from ADR provenance, App Builder provenance, runtime Ruleset identity, Dataset state, Ruleset/Dataset binding, and later repository history.

When Ruleset-owned governance artifacts are installed into the Dataset repository, the generated realization shall preserve sufficient Ruleset identity or traceability to determine their governing Ruleset source when consequential.

For equivalent resolved build inputs, App Builder shall deterministically construct the same generated repository trees and package-owned file content, subject to the existing FS-003 treatment of Git construction timestamps and commit identity.

## Validation

FS-004 Validation shall evaluate generated candidate repositories and mechanically verify obligations that are mechanically decidable.

Validation shall cover at least:

- repo-spec lifecycle installation in every `split-git` Ruleset repository;
- repo-spec lifecycle exclusion from the Dataset repository and all non-`split-git` profiles;
- exact correspondence between installed framework and the selected accepted repo-spec source;
- distinction among framework, product-development, runtime, provenance, and construction-input roles;
- canonical repo-spec Validation composition in the generated Ruleset repository;
- post-construction independence from App Builder and the supplying repo-spec checkout;
- mechanically sufficient Ruleset/Dataset binding material;
- separation of binding from provenance, history, and Dataset committed-state values;
- initialization determinacy for a fresh reasoning operation;
- traceability of Dataset-side Ruleset-governance artifacts where present; and
- deterministic generated-tree correspondence for equivalent resolved inputs.

Mechanical Validation does not establish future application-specific Design correctness or Dataset semantic correctness.

## Compatibility

FS-001, FS-002, and FS-003 remain applicable except where FS-004 deliberately strengthens the `split-git` Ruleset repository contract.

`single-file`, `split-files`, and `single-git` retain their accepted lifecycle behavior.

FS-004 changes newly generated `split-git` realizations by making repo-spec lifecycle management mandatory for the Ruleset repository and absent from the Dataset repository.

## Exclusions

FS-004 does not define:

- new ADR semantic roles;
- ADR ownership, application-instance, transition, compatibility, migration, binding, or initialization semantics;
- a universal Dataset schema;
- application-specific Ruleset or Dataset schemas;
- application-specific validation or migration semantics;
- a universal Ruleset/Dataset compatibility identifier or versioning system;
- one mandatory binding encoding or lookup protocol;
- a universal App Builder upgrade engine for generated repositories;
- automatic repo-spec framework upgrades after construction;
- repo-spec lifecycle management for `single-file`, `split-files`, or `single-git`;
- repo-spec Design/Planning lifecycle installation for Dataset repositories;
- runtime application save or commit services;
- provider-specific repo-spec semantics; or
- one universal physical layout for Dataset-side Ruleset-owned governance tooling.
